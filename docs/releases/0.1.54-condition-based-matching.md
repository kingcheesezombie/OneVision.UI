# OneVision.UI 0.1.54 — Condition-based matching editor

**Pattern:** OVP-MAPPING-RULE / OVC-MAPPING-RULE  
**Change:** New governed compact Conditions composition, no OVP-000 change  
**Status:** Pending verification and release

## Delivered

- Compact condition summaries replacing permanently displayed field trees.
- One transactional `OVDialog` editing surface for new and existing conditions, with dirty-discard confirmation.
- Per-condition Field to field and Field to value choices, plus operand-free operator behaviour.
- Reusable searchable hierarchical `OVStructuredFieldPicker`, preserving stable field keys and unavailable references.
- Typed text, number, date, boolean and controlled-value inputs; application-owned eligible operators.
- Visible AND/OR and nested groups, preserved condition identifiers, group callbacks, disabled/reorder/overflow actions.
- Optional `OVMappingRuleCondition.OperandKind` and optional operator semantic metadata, classified from authoritative operator definitions, not from a populated value alone.
- New-condition `ConditionCreateRequested` callback plus compatible `AddConditionRequested.Draft` adapter.
- Synthetic mixed and literal-only demo scenarios, including no automatic allocation eligibility for a literal-only example.

## Compatibility and ownership

Existing 0.1.53 saved field conditions, operator keys, groups and EAM governing-contract APIs remain supported. Optional kind metadata is omitted from JSON when absent. Existing applications must opt in to executing any newly supported condition kinds and validate target identification and processing eligibility themselves. OneVision.UI does not execute matches or modify historical evidence.

Legacy non-contract-driven composition remains explicitly available for consumers still migrating. The library must not be taken as proof of EAM application adoption.
